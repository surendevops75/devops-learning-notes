# EKS Logging

## 1. Overview

EKS logging provides centralized visibility into application, container, Kubernetes, Node, and AWS-related logs.

A production EKS logging architecture should make it possible to answer:

```text
What happened?
Which application was affected?
Which Pod and container produced the error?
Which Node was involved?
When did the problem start?
What happened immediately before the failure?
```

A typical architecture is:

```text
                         EKS CLUSTER
                              │
          ┌───────────────────┼───────────────────┐
          ↓                   ↓                   ↓
      Application Pods      Nodes             Kubernetes
          │                   │                   │
          ↓                   ↓                   ↓
       stdout/stderr       System Logs       Events
          │                   │                   │
          └───────────────────┼───────────────────┘
                              ↓
                       Log Collector
                              ↓
                          Logstash
                              ↓
                       Elasticsearch
                              ↓
                           Kibana
```

---

# 2. Why Logging Is Important

Metrics can tell us:

```text
CPU increased
Memory increased
Error rate increased
Latency increased
```

But logs can tell us:

```text
Database connection failed
Authentication failed
Configuration missing
Exception occurred
Request rejected
```

Therefore:

```text
Metrics → Detect
Logs    → Investigate
```

# 6. Container Logs

Containers commonly write application output to:

```text
stdout
stderr
```

Kubernetes and the container runtime make these logs accessible.

For example:

```bash
kubectl logs <pod-name>
```

For a specific container:

```bash
kubectl logs <pod-name> -c <container-name>
```

---

# 7. Viewing EKS Pod Logs

Basic command:

```bash
kubectl logs <pod-name>
```

Previous container instance:

```bash
kubectl logs <pod-name> --previous
```

Follow logs:

```bash
kubectl logs -f <pod-name>
```

Specific namespace:

```bash
kubectl logs <pod-name> -n <namespace>
```

These commands are useful for immediate troubleshooting.

---

# 8. Why Centralized Logging Is Required

Running:

```bash
kubectl logs
```

is useful for individual troubleshooting.

But a production EKS cluster may contain:

```text
100+ Pods
10+ Nodes
Multiple namespaces
Multiple microservices
```

Manually checking each Pod is inefficient.

Centralized logging provides:

```text
All logs
   ↓
One platform
   ↓
Search
Filter
Correlate
Analyze
```

---

# 9. Centralized Logging Architecture

Without centralized logging:

```text
Node-1 → Local logs
Node-2 → Local logs
Node-3 → Local logs
```

With centralized logging:

```text
Node-1 ─┐
Node-2 ─┼──→ Log Collector → Logstash → Elasticsearch
Node-3 ─┘                                  ↓
                                         Kibana
```

This allows engineers to search logs across the entire cluster.

---

# 10. Log Collector

The log collector runs close to the workloads.

A common Kubernetes pattern is:

```text
DaemonSet
   ↓
One logging agent per Node
```

Architecture:

```text
Node-1 → Collector
Node-2 → Collector
Node-3 → Collector
```

The collector reads logs from containers and forwards them to the centralized logging pipeline.

---

# 11. Why DaemonSet Is Common for Log Collection

A DaemonSet ensures a collector runs on every eligible Node.

Example:

```text
10 Nodes
   ↓
10 Collector Pods
```

When a new Node is added:

```text
New Node
   ↓
DaemonSet
   ↓
Collector Pod automatically created
```

This makes log collection scalable with the cluster.

# 20. Structured Logging

Applications should preferably produce structured logs such as JSON.

Example:

```json

  "timestamp": "2026-08-11T09:30:10Z",
  "level": "ERROR",
  "service": "payment",
  "message": "Database connection failed",
  "status": 500
```

Structured logs are easier to:

```text
Parse
Search
Filter
Aggregate
Visualize
```

# 43. Logging High Availability

Production logging should avoid a single point of failure.

Conceptually:

```text
Collectors
   │
   ├──→ Logstash-1
   ├──→ Logstash-2
   └──→ Logstash-3
          │
          ↓
   Elasticsearch Cluster
          │
          ↓
        Kibana
```

The exact design depends on log volume and availability requirements.

---

# 44. Elasticsearch High Availability

A production Elasticsearch cluster can use multiple Nodes.

Example:

```text
Elasticsearch
│
├── Node-1
├── Node-2
└── Node-3
```

# 76. Interview Question

### How would you implement centralized logging in EKS?

**Answer:**

I would deploy a log collector as a DaemonSet so that each Node has a logging agent collecting container logs. The collector would forward logs to Logstash for parsing, filtering, and Kubernetes metadata enrichment. Logstash would send the processed events to Elasticsearch for indexing and storage, and Kibana would provide centralized search and dashboards. I would also monitor the logging pipeline itself for ingestion failures, backlog, storage, and availability.

---

# 77. Interview Question

### Why use a DaemonSet for log collection?

**Answer:**

A DaemonSet ensures that a logging collector runs on every eligible Node. When a new Node is added, Kubernetes automatically schedules the collector there, so the logging architecture scales with the cluster. This is particularly useful for collecting container and Node-level logs.

# 78. Interview Question

### How would you troubleshoot missing logs in EKS?

**Answer:**

I would start by checking whether the application is actually writing to stdout or stderr using `kubectl logs`. Then I would check the collector Pod and its configuration, followed by Logstash input and pipeline health, Elasticsearch indexing and storage, and finally Kibana filters and index patterns. I would trace the logging pipeline from the source to the visualization layer to identify where the logs are being lost.

---

# 79. Interview Question

### How do you prevent Elasticsearch from running out of storage?

**Answer:**

I monitor disk usage and index growth, define retention policies, remove or archive data according to requirements, control log volume, and investigate unexpected ingestion increases. I also monitor Elasticsearch cluster health and ensure adequate storage capacity for normal growth and operational headroom.

---

# 80. Interview Question

### How would you correlate an EKS log with a distributed trace?

**Answer:**

I would include a request ID and, when tracing is enabled, trace ID and span ID in application logs. Then I can search Kibana using the trace ID and correlate the log entries with the corresponding trace in Jaeger. This allows me to move from an error message to the exact service and span where the failure or latency occurred.

---

# 81. Interview Question

### What happens if Logstash cannot process logs fast enough?

**Answer:**

A backlog can build up between the input and output stages. I would monitor input rate, output rate, queue size, CPU, memory, and Elasticsearch performance. Depending on the bottleneck, I would optimize the pipeline, improve Elasticsearch performance, scale Logstash, or reduce unnecessary log volume.

---

# 82. Interview Question

### How would you troubleshoot a sudden increase in EKS log volume?

**Answer:**

I would first identify which service, namespace, Pod, or Node is generating the additional logs. Then I would inspect the log level and top error messages. A sudden increase may be caused by a traffic spike, application error loop, debug logging, retry behavior, or a deployment regression. I would correlate the increase with application metrics and deployment history.

---

# 83. Interview Question

### Why is centralized logging important in a microservices environment?

**Answer:**

A microservices application can have many services distributed across multiple Nodes and Pods. Centralized logging provides one searchable location where logs can be filtered by service, namespace, Pod, Node, version, request ID, and trace ID. This makes it much easier to follow failures across service boundaries.

```text
             ↓                         ↓
```

**Key principle:** EKS logging should provide centralized, searchable, structured visibility across application Pods, Nodes, Kubernetes Events, and the surrounding AWS infrastructure. A production logging pipeline commonly follows **Collect → Process → Store → Search → Visualize**. In an EKS environment, a DaemonSet-based collector provides Node coverage, Logstash can process and enrich events, Elasticsearch provides indexing and storage, and Kibana provides investigation and dashboards. The most effective troubleshooting comes from correlating logs with Prometheus metrics, Kubernetes Events, and distributed traces.
