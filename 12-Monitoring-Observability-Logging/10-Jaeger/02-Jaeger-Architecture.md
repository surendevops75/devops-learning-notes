# Jaeger Architecture

## 1. Overview

Jaeger is a distributed tracing platform designed to collect, store, query, and visualize traces generated by distributed applications.

A simplified architecture is:

```text
Application
     ↓
Instrumentation
     ↓
Trace Data
     ↓
Jaeger Ingestion
     ↓
Storage
     ↓
Jaeger Query
     ↓
Jaeger UI
```

In a modern Kubernetes environment using OpenTelemetry:

```text
Applications
     ↓
OpenTelemetry SDK
     ↓
OpenTelemetry Collector
     ↓
Jaeger
     ↓
Trace Storage
     ↓
Jaeger Query
     ↓
Jaeger UI
```

The architecture separates **trace generation, collection, ingestion, storage, querying, and visualization**.

---

# 2. Why Jaeger Architecture Matters

In a microservices environment, one user request can cross many services.

```text
User
 ↓
Frontend
 ↓
Orders
 ↓
Payment
 ↓
Inventory
 ↓
Database
```

Each service may generate multiple spans.

Jaeger needs an architecture capable of:

```text
Receiving traces
Processing traces
Storing traces
Searching traces
Visualizing traces
Scaling with traffic
```

A production architecture must also address:

```text
High availability
Scalability
Security
Storage
Sampling
Failure handling
Cost
```

```text
     ↓
```

```text
     ↓
```

A production architecture commonly places the OpenTelemetry Collector between applications and Jaeger.

```text
Application
     ↓
OTel SDK
     ↓
OTel Collector
     ↓
Jaeger
```

The Collector can provide:

```text

Filtering
Transformation
Enrichment
Sampling
Retry
Routing
```

This makes the telemetry pipeline more flexible.

# 7. Collector Agent Architecture

In Kubernetes, an Agent can run as a DaemonSet.

```text
Node 1
├── Application Pods
└── OTel Agent

Node 2
├── Application Pods
└── OTel Agent

Node 3
├── Application Pods
└── OTel Agent
```

Applications send telemetry to a local Collector Agent.

```text
Application
     ↓
Local Agent
```

This reduces the need for every application to know about centralized backend endpoints.

# 19. Trace Context Propagation

Trace context must travel between services.

Example:

```text
Orders
   ↓
HTTP Request
   ↓
traceparent
   ↓
Payment
```

Payment extracts the incoming context and creates a child span.

Therefore:

```text
Orders Trace ID
       =
Payment Trace ID
```

for the same distributed request.

```text

   ↓
```

# 26. Latency Propagation

Suppose:

```text

        ↓
      2 sec
```

```text
Payment
   ↓
2 sec
```

```text
Orders
   ↓

   ↓
```


# 27. Sampling Architecture

High traffic produces large numbers of traces.

Therefore:

```text
Applications
     ↓
Collector
     ↓
Sampling
     ↓
Jaeger
```

Possible strategy:

```text
Errors → Keep 100%
Slow traces → Keep 100%
Normal traces → Sample 5%
```

The exact percentages depend on requirements.

---

# 28. Head Sampling

Head sampling makes the decision early.

```text
Request
  ↓
Sampler
 ┌───────┐
Keep   Drop
```

Advantages:

```text
Low overhead
Lower network traffic
Simple architecture
```

Disadvantage:

```text
The final outcome of the request may not yet be known.
```

---

# 29. Tail Sampling

Tail sampling waits for more information.

```text
Trace
 ↓
Collect
 ↓
Evaluate
 ↓
Sampling Decision
```

Example:

```text
Error trace → KEEP
Slow trace → KEEP
Normal trace → SAMPLE
```

This is useful for production environments where important traces should be retained.

# 31. High Availability

A production system should avoid:

```text
Application
     ↓
Single Gateway
     ↓
Jaeger
```

because the Gateway becomes a single point of failure.

Instead:

```text
                    OTel Gateway
                 /       |       \
                ↓        ↓        ↓
              GW-1     GW-2     GW-3
                 \       |       /
                      Jaeger
```

---

# 32. Availability Zones

For EKS:

```text
AZ-A
 └── Gateway-1

AZ-B
 └── Gateway-2

AZ-C
 └── Gateway-3
```

This reduces the effect of a single AZ failure.

The same principle should be applied to other highly available components where supported.

---

# 33. Query High Availability

Multiple Query replicas can be deployed when the workload requires it.

```text
                Jaeger Query Service
                         │
            ┌────────────┼────────────┐
            ↓            ↓            ↓
         Query-1      Query-2      Query-3
```

The Service distributes requests across healthy replicas.

---

# 34. Storage High Availability

Jaeger Query can have multiple replicas, but the storage backend must also be reliable.

```text
Jaeger Query
      ↓
Storage Cluster
 ┌────┼────┐
 ↓    ↓    ↓
Node Node Node
```

If storage is a single-instance dependency, the overall system still has a major failure point.

---

# 35. Failure Isolation

Production architecture should isolate failures.

Example:

```text
Gateway-1
    X

Gateway-2
    ↓
Healthy

Gateway-3
    ↓
Healthy
```

Application telemetry can continue.

Similarly:

```text
Query-1
    X

Query-2
    ↓
Healthy
```

The UI can continue working.

---

# 36. Backend Failure

Suppose Jaeger storage becomes unavailable:

```text
Collector
    ↓
Jaeger
    ↓
Storage
    X
```

The Collector should use appropriate:

```text
Queueing
Retry
Timeouts
Backpressure
Sampling
```

The goal is to prevent backend failure from causing uncontrolled resource consumption.

---

# 37. Collector Backpressure

Suppose:

```text
Incoming = 100,000 spans/sec
Backend capacity = 50,000 spans/sec
```

Then:

```text
Queue ↑
Memory ↑
```

Eventually resources may become exhausted.

Therefore use:

```text
Bounded queues
Memory limits
Sampling
Load balancing
Backend scaling
```


Suppose users report slow checkout.

```text

   ↓

```

```text
Jaeger
   ↓
Find slow checkout trace
```

Trace:

```text

   ↓
Orders
   ↓
Payment
   ↓
External Gateway
```

The Payment span takes:

```text
1.8 seconds
```

Then:

```text
Kibana
   ↓
```

# 68. Production Design Principles

A good Jaeger architecture should follow:

```text
1. Separate telemetry generation from backend storage.
2. Use OpenTelemetry for instrumentation.
3. Use Collectors for centralized telemetry processing.
4. Use Agents for local Kubernetes collection where appropriate.
5. Use Gateway Collectors for scalable processing.
6. Use sampling to control trace volume.
7. Use durable storage in production.
8. Make critical components highly available.
9. Distribute replicas across failure domains.
10. Secure telemetry and UI access.
11. Protect sensitive attributes.
12. Monitor the tracing platform itself.
13. Manage deployment through GitOps.
14. Test upgrades before production.
15. Maintain rollback and disaster-recovery procedures.
```


# 75. Final Mental Model

Remember Jaeger architecture as:

```text
                 APPLICATIONS
                      │
                      ↓
               OpenTelemetry
                      │
                      ↓
               Collector Agents
                      │
                      ↓
              Collector Gateways
                      │
             ┌────────┴────────┐
             ↓                 ↓
          Process           Sample
             └────────┬────────┘
                      ↓
                   Jaeger
                      │
                      ↓
                Trace Storage
                      │
                      ↓
                Jaeger Query
                      │
                      ↓
                  Jaeger UI
```

The complete production model is:

```text
Applications
    ↓
OpenTelemetry SDK
    ↓
OTel Agent
    ↓
OTel Gateway
    ↓
Batch / Filter / Enrich / Sample
    ↓
Jaeger
    ↓
Durable Storage
    ↓
Jaeger Query
    ↓
Jaeger UI
```

The most important architectural principle is:

**Jaeger should be treated as one part of a distributed tracing platform, not as an isolated UI. OpenTelemetry generates and transports telemetry, Collectors provide scalable processing and control, Jaeger provides trace ingestion and querying, durable storage preserves trace data, and the Jaeger UI allows engineers to investigate distributed requests. In production EKS environments, the architecture should be horizontally scalable, highly available across failure domains, securely networked, resource-controlled, monitored, and managed through GitOps.**
