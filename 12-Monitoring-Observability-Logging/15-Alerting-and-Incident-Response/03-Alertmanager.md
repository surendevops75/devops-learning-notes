# Alertmanager

## 1. Overview

Alertmanager is a component in the Prometheus monitoring ecosystem responsible for handling alerts generated by Prometheus.

Prometheus is responsible for:

```text
Collecting Metrics
        ↓
Evaluating Alert Rules
        ↓
Generating Alerts
```

Alertmanager is responsible for:

```text
Receiving Alerts
        ↓
Grouping
        ↓
Deduplication
        ↓
Routing
        ↓
Silencing
        ↓
Inhibition
        ↓
Notification
```

The overall architecture is:

```text
Targets
   ↓
Exporters
   ↓
Prometheus
   ↓
Alert Rules
   ↓
Alertmanager
   ↓
┌────────────┬─────────────┬──────────────┐
↓            ↓             ↓
Slack       Email       PagerDuty
```

---

# 2. Why Alertmanager Is Needed

Prometheus can detect an alert condition, but production environments require additional alert management.

For example:

```text
Prometheus
    ↓
HighCPUUsage
    ↓
Alertmanager
```

Alertmanager can then decide:

```text
Which team?
Which channel?
What severity?
Should alerts be grouped?
Is this alert already sent?
Is it currently silenced?
Should another alert be suppressed?
```

Therefore:

```text
Prometheus
=
Detection

Alertmanager
=
Alert Management + Notification
```

---

# 3. Alertmanager Responsibilities

The major responsibilities of Alertmanager are:

```text
1. Alert Reception
2. Alert Routing
3. Alert Grouping
4. Alert Deduplication
5. Alert Inhibition
6. Alert Silencing
7. Notification
8. Notification Retry
9. Alert Resolution Notification
```

These capabilities make Alertmanager useful for production operations.

# 9. Global Configuration

The `global` section contains default settings.

Example:

```yaml
global:
  resolve_timeout: 5m
```

It can also contain notification integration defaults depending on the configuration.

The purpose is to define common configuration that applies across Alertmanager.

---

# 10. Resolve Timeout

Example:

```yaml
global:
  resolve_timeout: 5m
```

This defines how long Alertmanager waits before considering an alert resolved when resolution information is not received as expected.

The exact behavior depends on how the alert source and notification path are configured.

---

# 11. Route

The route determines where alerts should go.

Example:

```yaml
route:
  receiver: default-receiver
```

Conceptually:

```text
Alert
  ↓
Route
  ↓
Receiver
```

Routes can be nested to implement more specific routing.

---

# 12. Default Receiver

A default receiver catches alerts that do not match more specific routes.

Example:

```yaml
route:
  receiver: default-receiver
```

This provides a fallback.

Architecture:

```text
Alert
  │
  ├── Matches Specific Route → Specific Receiver
  │
  └── No Match → Default Receiver
```

---

Then a route can send alerts to:


# 20. Grouping

Grouping combines related alerts into a single notification.

Example:

```text
Node Failure
   ↓
Pod Alerts
   ↓
Service Alerts
```

Without grouping:

```text
10 Alerts
↓
10 Notifications
```

With grouping:

```text
10 Alerts
↓
1 Grouped Notification
```

---

# 21. Why Grouping Matters

Suppose an EKS node fails.

That can cause:

```text
NodeNotReady
PodPending
PodRestart
DeploymentUnavailable
ServiceError
```

Without grouping:

```text
Many notifications
```

With grouping:

```text
Related alerts
      ↓
One notification
      ↓
Engineer investigates root cause
```

This reduces alert fatigue.

---

# 22. `group_by`

Example:

```yaml
route:
  group_by:
    - alertname
    - cluster
    - namespace
```

Alerts with matching grouping labels can be grouped together.

The correct grouping keys depend on how the organization handles incidents.

---

# 23. `group_wait`

`group_wait` controls how long Alertmanager waits before sending the first notification for a new alert group.

Example:

```yaml
group_wait: 30s
```

Conceptually:

```text
First Alert
    ↓
Wait 30 seconds
    ↓
Check for Related Alerts
    ↓
Send Grouped Notification
```

This allows closely related alerts to be grouped together.

---

# 24. `group_interval`

`group_interval` controls how long Alertmanager waits before sending an update for an already existing alert group.

Example:

```yaml
group_interval: 5m
```

Conceptually:

```text
Existing Alert Group
       ↓
New Related Alert
       ↓
Wait
       ↓
Send Group Update
```

---

# 25. `repeat_interval`

`repeat_interval` controls how often Alertmanager repeats notifications for an alert that remains active.

Example:

```yaml
repeat_interval: 4h
```

Conceptually:

```text
Alert Fires
   ↓
Notification
   ↓
Still Firing
   ↓
4 Hours
   ↓
Repeat Notification
```

This prevents continuous notification spam while still reminding teams about unresolved problems.

---

# 26. Grouping Example

```yaml
route:
  receiver: platform-team

  group_by:
    - alertname
    - cluster

  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
```

This configuration means:

```text
Group by alert name and cluster
        ↓
Wait 30 seconds for initial grouping
        ↓
Send updates every 5 minutes when applicable
        ↓
Repeat unresolved notifications every 4 hours
```

---

# 27. Deduplication

Alertmanager performs deduplication to avoid sending repeated notifications for the same alert state.

Example:

```text
Prometheus
    ↓
HighCPUUsage
    ↓
Alertmanager
```

If the same alert is repeatedly received:

```text
HighCPUUsage
HighCPUUsage
HighCPUUsage
```

Alertmanager can avoid unnecessary duplicate notifications.

---

# 28. Why Deduplication Matters

Without deduplication:

```text
One Incident
    ↓
Multiple Alert Sources
    ↓
Multiple Notifications
```

This can create:

```text
Alert Fatigue
Notification Spam
Confusion
```

Deduplication keeps the notification path manageable.

---

# 29. Inhibition

Inhibition prevents certain alerts from generating notifications when another alert is already firing.

Example:

```text
Node Down
   ↓
Pods Down
   ↓
Services Unhealthy
```

The node failure may be the primary problem.

Instead of notifying:

```text
Node Alert
+
Pod Alerts
+
Service Alerts
```

inhibition can suppress secondary alerts.

---

# 30. Inhibition Example

Conceptually:

```yaml
inhibit_rules:
  - source_matchers:
      - alertname="NodeDown"

    target_matchers:
      - severity="warning"

    equal:
      - cluster
      - node
```

Meaning:

```text
NodeDown
   ↓
Suppress related warning alerts
```

The exact matchers should be designed carefully.

---

# 31. Inhibition vs Grouping

These concepts are different.

### Grouping

Combines alerts:

```text
Alert A
Alert B
Alert C
   ↓
One Notification
```

### Inhibition

Suppresses alerts:

```text
Primary Alert
     ↓
Secondary Alert Suppressed
```

So:

```text
Grouping = Combine

Inhibition = Suppress
```

---

# 32. Inhibition vs Silencing

### Inhibition

Automatically suppresses alerts based on another alert.

```text
NodeDown
   ↓
Suppress Pod Alerts
```

### Silencing

Manually suppresses matching alerts for a defined period.

```text
Planned Maintenance
   ↓
Create Silence
   ↓
Suppress Expected Alerts
```

Therefore:

```text
Inhibition = Rule-Based Suppression

Silence = Operator-Defined Suppression
```

---

# 33. Silences

A silence prevents notifications for matching alerts.

Example:

```text
Planned Maintenance
       ↓
Create Silence
       ↓
Affected Alerts
       ↓
No Notifications
```

A silence should include:

```text
Matchers
Start Time
End Time
Creator
Comment / Reason
```

---

# 34. Silence Example

Conceptually:

```text
Matchers:

environment = production
service = payment

Duration:

01:00 - 02:00

Reason:

Planned deployment
```

During that period:

```text
Matching Alerts
      ↓
Silenced
```

---

# 35. Silence Best Practices

Always provide:

```text
Reason
Owner
Start Time
End Time
Scope
```

Good:

```text
Reason:
Planned database maintenance

Owner:
Platform Team

End:
02:00
```

Bad:

```text
Silence everything
for 7 days
```

Silences should be narrow and temporary.


# 47. Alertmanager High Availability


High availability helps avoid having a single Alertmanager instance as a notification bottleneck.

---

# 48. Why Alertmanager HA Matters

Suppose:

```text
Prometheus
    ↓
Single Alertmanager
    X
```

If Alertmanager fails:

```text
Prometheus may still detect alerts
```

but:

```text
Notifications may not reach engineers
```

This creates a dangerous observability failure.

Therefore critical environments should consider Alertmanager high availability.

# 63. Alertmanager Configuration Example

```yaml
global:
  resolve_timeout: 5m

route:
  receiver: default-receiver

  group_by:
    - alertname
    - cluster
    - namespace

  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

  routes:

    - matchers:
        - severity="critical"
        - environment="production"
      receiver: critical-production

    - matchers:
        - severity="warning"
        - environment="production"
      receiver: warning-production

    - matchers:
        - environment="staging"
      receiver: staging-alerts

receivers:

  - name: default-receiver

  - name: critical-production

  - name: warning-production

  - name: staging-alerts
```

This demonstrates the structure without tying it to a specific organization's credentials or endpoints.

# 89. Interview Question

## What is alert grouping?

**Answer:**

Alert grouping combines related alerts into a single notification.

For example:

```text
Node Failure
   ↓
Pod Alerts
   ↓
Service Alerts
```

Instead of receiving many notifications, Alertmanager can group related alerts.

This reduces alert fatigue.

---

# 90. Interview Question

## What is alert inhibition?

**Answer:**

Inhibition suppresses certain alerts when another alert is already firing.

For example:

```text
NodeDown
   ↓
Pods Unhealthy
```

If NodeDown is already firing, dependent pod alerts may be inhibited.

This helps engineers focus on the primary failure.

---

# 91. Interview Question

## What is alert silencing?

**Answer:**

A silence temporarily suppresses notifications for alerts matching specified conditions.

A common use case is planned maintenance.

Example:

```text
Maintenance
    ↓
Create Silence
    ↓
Expected Alerts Suppressed
```

Silences should be temporary, scoped, and documented.

---

# 92. Interview Question

## What is the difference between grouping and inhibition?

**Answer:**

Grouping combines multiple alerts into one notification.

```text
A + B + C
    ↓
One Notification
```

Inhibition suppresses one alert because another alert explains the condition.

```text
Primary Alert
    ↓
Secondary Alert Suppressed
```

Therefore:

```text
Grouping = Combine

Inhibition = Suppress
```

# 93. Interview Question

## What are `group_wait`, `group_interval`, and `repeat_interval`?

**Answer:**

`group_wait` controls how long Alertmanager waits before sending the first notification for a new group.

```text
group_wait
```

`group_interval` controls how long it waits before sending updates for an existing group.

```text
group_interval
```

`repeat_interval` controls how often notifications are repeated for alerts that remain firing.

```text
repeat_interval
```

Conceptually:

```text
First Alert
   ↓
group_wait
   ↓
Initial Notification
   ↓
group_interval
   ↓
Updates
   ↓
repeat_interval
   ↓
Repeated Notification
```

# 103. Alert Flapping

Alert flapping occurs when an alert repeatedly changes between:

```text
Firing
Resolved
Firing
Resolved
```

Example:

```text
CPU:
89%
91%
89%
92%
88%
91%
```

If the threshold is:

```text
90%
```

the alert may repeatedly fire and resolve.

Possible solutions:

```text
Adjust Threshold
Add Duration
Use Hysteresis-Like Logic Where Appropriate
Review Metric
Investigate Underlying Instability
```
