# Log Levels

Log levels define the severity and importance of events generated by an application or system.

They help engineers distinguish between:

```
Normal operational information
Important warnings
Application failures
Serious system failures
Detailed debugging information
```

A well-designed logging strategy uses log levels consistently across applications, services, containers, and environments.

---

# 1. Why Log Levels Matter

Without log levels, all events may appear equally important.

Example:

```
Application started
User logged in
Database connected
Payment failed
Service unavailable
```

If everything is simply:

```
LOG
```

it becomes difficult to prioritize events.

With log levels:

```
INFO   Application started
INFO   Database connected
WARN   Database connection pool near limit
ERROR  Payment failed
FATAL  Service cannot initialize
```

Engineers can immediately identify important events.

---

# 2. Common Log Levels

The most commonly used levels are:

```
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

Not every logging framework supports exactly the same levels.

Some systems use:

```
DEBUG
INFO
WARN
ERROR
```

Others may include:

```
TRACE
FATAL
```

The exact naming depends on the logging framework.

---

# 3. Log Level Hierarchy

A common severity hierarchy is:

```
TRACE
  ↓
DEBUG
  ↓
INFO
  ↓
WARN
  ↓
ERROR
  ↓
FATAL
```

Moving downward generally means increasing severity.

---

# 4. TRACE

TRACE is typically the most detailed logging level.

It is useful when extremely detailed execution information is required.

Example:

```
TRACE Entering OrderService.createOrder()

TRACE Validating customer information

TRACE Calling inventory service

TRACE Inventory response received
```

TRACE logging can generate very large volumes.

It is generally not enabled continuously in production.

---

# 5. When to Use TRACE

TRACE can be useful for:

```
Detailed Execution Flow
Complex Debugging
Framework Internals
Temporary Investigation
```

Example:

```
TRACE method=calculateDiscount
customer_type=premium
discount_rule=rule_03
```

It should be enabled carefully because of volume and potential data exposure.

---

# 6. DEBUG

DEBUG provides detailed information useful for developers and engineers troubleshooting an application.

Examples:

```
DEBUG Connecting to database

DEBUG Request received from payment-service

DEBUG Cache lookup completed

DEBUG Configuration loaded
```

DEBUG is generally more detailed than INFO.

---

# 7. When to Use DEBUG

DEBUG is useful for:

```
Development
Testing
Troubleshooting
Temporary Production Investigation
```

Example:

```
DEBUG service=order-service
operation=create_order
database_connection=pool-3
```

DEBUG logs should be reviewed for sensitive information before being enabled in production.

---

# 8. INFO

INFO represents normal application or system activity.

Examples:

```
INFO Application started

INFO Database connection established

INFO Deployment completed

INFO Order created

INFO User authenticated
```

INFO is normally the default production logging level for many applications.

---

# 9. When to Use INFO

Use INFO for meaningful operational events.

Good examples:

```
Application Startup
Application Shutdown
Configuration Loaded
Important Business Event
Deployment Event
Dependency Connection
Scheduled Job Started
Scheduled Job Completed
```

Avoid logging every minor internal operation at INFO.

---

# 10. INFO Should Not Become Noise

Bad:

```
INFO Received health check

INFO Received health check

INFO Received health check

INFO Received health check
```

If an application receives thousands of health checks per minute, logging every successful health check can create unnecessary volume.

Better:

```
Log important failures
```

or:

```
Use DEBUG for detailed successful health-check information
```

---

# 11. WARN

WARN indicates something unexpected or potentially problematic happened, but the application can continue operating.

Examples:

```
WARN Database connection pool near limit

WARN External API response time exceeded threshold

WARN Disk usage reached 80%

WARN Retry attempt 2 of 3
```

The system is not necessarily broken, but attention may be required.

---

# 12. When to Use WARN

WARN is appropriate when:

```
A Resource Is Near a Limit
A Retry Is Required
A Dependency Is Degraded
A Configuration Is Suspicious
A Fallback Is Being Used
An Operation Is Taking Longer Than Expected
```

Example:

```
WARN payment-service timeout
retry=2
max_retries=3
```

---

# 13. WARN Does Not Always Mean Incident

A common mistake is treating every WARN as a production incident.

Example:

```
WARN Retry attempt 1 of 3
```

This may be completely normal.

But:

```
WARN Retry limit nearly exhausted
```

may deserve attention.

Log severity should reflect the operational impact.

---

# 14. ERROR

ERROR indicates a failure that affected an operation or request.

Examples:

```
ERROR Database query failed

ERROR Payment processing failed

ERROR External API request failed

ERROR Failed to process order
```

The application may continue running after an ERROR.

---

# 15. When to Use ERROR

Use ERROR when:

```
An Operation Failed
A Request Could Not Be Completed
A Dependency Call Failed
Data Processing Failed
An Unexpected Exception Occurred
```

Example:

```
ERROR Failed to create order
order_id=12345
dependency=payment-service
error=timeout
```

---

# 16. ERROR Does Not Always Mean Application Down

An application can remain healthy while producing ERROR logs.

Example:

```
10,000 requests

9,990 successful

10 failed
```

The application is still running, but those failed operations may require investigation.

This is why ERROR rate should be considered together with metrics.

---

# 17. FATAL

FATAL represents a severe failure that prevents the application or major component from continuing.

Examples:

```
FATAL Unable to initialize application

FATAL Required configuration missing

FATAL Cannot connect to critical database

FATAL Unable to bind application port
```

Depending on the application framework, a FATAL event may cause process termination.

---

# 18. When to Use FATAL

Use FATAL only when the system cannot reasonably continue.

Example:

```
FATAL Database migration failed
application startup aborted
```

Do not use FATAL for normal request failures.

---

# 19. TRACE vs DEBUG

TRACE:

```
Extremely Detailed
Execution-Level Information
High Volume
```

DEBUG:

```
Detailed Troubleshooting Information
Developer-Oriented
Lower Volume Than TRACE
```

Example:

```
TRACE Entering method A
TRACE Entering method B
TRACE Variable validation

DEBUG Order creation started
DEBUG Payment service called
```

---

# 20. DEBUG vs INFO

DEBUG:

```
Detailed technical information
```

INFO:

```
Important normal operational events
```

Example:

```
DEBUG Loading configuration property X

INFO Application started successfully
```

---

# 21. INFO vs WARN

INFO:

```
Normal expected behavior
```

WARN:

```
Unexpected or potentially problematic behavior
```

Example:

```
INFO Database connection established

WARN Database connection pool at 80%
```

---

# 22. WARN vs ERROR

WARN:

```
Problem may require attention
```

ERROR:

```
An operation actually failed
```

Example:

```
WARN Payment API response is slow

ERROR Payment API request failed
```

---

# 23. ERROR vs FATAL

ERROR:

```
Individual operation or component failed
```

FATAL:

```
Application or critical component cannot continue
```

Example:

```
ERROR Order creation failed

FATAL Application cannot start because required configuration is missing
```

---

# 24. Common Log Level Table

| Level | Severity  | Typical Meaning              | Production Usage |
| ----- | --------- | ---------------------------- | ---------------- |
| TRACE | Very Low  | Extremely detailed execution | Rare             |
| DEBUG | Low       | Troubleshooting details      | Controlled       |
| INFO  | Normal    | Normal operations            | Common           |
| WARN  | Medium    | Potential problem            | Common           |
| ERROR | High      | Operation failed             | Common           |
| FATAL | Very High | Application cannot continue  | Rare             |

---

# 25. Production Default

A common production default is:

```
INFO
```

This allows important operational information to be recorded without generating excessive debug-level volume.

However, the correct default depends on:

```
Application
Log Volume
Operational Requirements
Compliance
Cost
Troubleshooting Needs
```

---

# 26. Development Environment

Development may use:

```
DEBUG
```

or:

```
TRACE
```

because developers often need detailed execution information.

Example:

```
TRACE
DEBUG
INFO
WARN
ERROR
```

---

# 27. Testing Environment

Testing environments often use:

```
DEBUG
```

This provides enough information to investigate test failures.

Example:

```
DEBUG API request
DEBUG database operation
DEBUG test execution
ERROR test failure
```

---

# 28. Staging Environment

Staging should be close to production behavior.

A common approach is:

```
INFO
```

with the ability to temporarily increase specific components to:

```
DEBUG
```

This helps prevent staging from becoming dramatically different from production.

---

# 29. Production Environment

Production commonly uses:

```
INFO
```

with:

```
WARN
ERROR
```

available for important events.

DEBUG can be enabled temporarily for targeted troubleshooting if the application supports dynamic configuration.

---

# 30. Dynamic Log Level

Some production systems allow log levels to be changed without restarting the application.

Example:

```
Current:
INFO
```

Temporary:

```
DEBUG
```

After investigation:

```
DEBUG → INFO
```

This can be useful during incidents.

However, access to log-level changes should be controlled.

---

# 31. Why Not Enable DEBUG Permanently?

Permanent DEBUG logging can create:

```
High Log Volume
Increased Storage
Higher Network Usage
Higher CPU Usage
Increased Search Cost
Sensitive Data Exposure
More Log Noise
```

DEBUG should be enabled when it provides operational value.

---

# 32. Temporary DEBUG During Incident

Example incident:

```
Payment latency increased
```

Normal:

```
INFO
```

Temporarily:

```
DEBUG
```

Investigate:

```
External API
Database
Retry Behavior
Request Flow
```

After resolution:

```
DEBUG → INFO
```

This gives additional context without permanently increasing log volume.

---

# 33. Component-Level Logging

Instead of enabling DEBUG for the entire application, configure it for a specific component.

Example:

```
Application:
INFO

payment.client:
DEBUG

database:
INFO
```

This is safer and generates less noise.

---

# 34. Package-Level Logging

Many application frameworks allow log levels to be configured by package or module.

Example:

```
com.company.orders = INFO

com.company.orders.payment = DEBUG
```

This enables targeted troubleshooting.

---

# 35. Service-Level Logging

In a microservices architecture:

```
User Service → INFO

Order Service → INFO

Payment Service → DEBUG
```

Only the service under investigation receives increased verbosity.

This is a better approach than enabling DEBUG everywhere.

---

# 36. Log Levels in Microservices

Example:

```
User Service
    INFO

Product Service
    INFO

Cart Service
    INFO

Order Service
    WARN

Payment Service
    DEBUG
```

During a payment incident, only Payment Service may temporarily use DEBUG.

---

# 37. Log Level Configuration

Log levels should ideally be configurable through:

```
Environment Variables
Configuration Files
Application Configuration
Configuration Management
```

Example:

```
LOG_LEVEL=INFO
```

Then:

```
LOG_LEVEL=DEBUG
```

can be used temporarily when required.

Secrets should not be stored in plain configuration files.

---

# 38. Environment Variables

Example:

```
LOG_LEVEL=INFO
```

Application behavior:

```
LOG_LEVEL=INFO
    ↓
INFO/WARN/ERROR
```

If:

```
LOG_LEVEL=DEBUG
```

then:

```
DEBUG/INFO/WARN/ERROR
```

are emitted depending on the framework's filtering behavior.

---

# 39. Log Level Filtering

Suppose the application is configured for:

```
INFO
```

Then:

```
TRACE → Not Logged
DEBUG → Not Logged
INFO  → Logged
WARN  → Logged
ERROR → Logged
FATAL → Logged
```

This reduces unnecessary log volume.

---

# 40. Log Level Filtering Flow

```
Application Event
      |
      ↓
   Log Level
      |
      ↓
Configured Threshold
      |
      ↓
Should It Be Logged?
   /           \
 YES            NO
  |              |
  ↓              ↓
Output          Drop
```

---

# 41. Severity Threshold

If the threshold is:

```
WARN
```

then typically:

```
TRACE → Drop
DEBUG → Drop
INFO  → Drop
WARN  → Keep
ERROR → Keep
FATAL → Keep
```

This is useful when an application is generating too much information.

---

# 42. Choosing the Correct Level

Ask:

```
Is this normal behavior?

    ↓
   INFO

Could this become a problem?

    ↓
   WARN

Did an operation fail?

    ↓
   ERROR

Can the application continue?

    ↓
   ERROR

Can the application no longer continue?

    ↓
   FATAL

Is detailed troubleshooting information needed?

    ↓
   DEBUG

Is extremely detailed execution information required?

    ↓
   TRACE
```

---

# 43. Logging Business Events

Business events can be logged at INFO.

Example:

```
INFO Order created
order_id=12345
customer_type=premium
```

But avoid logging sensitive customer information.

---

# 44. Logging Successful Requests

Not every successful request needs to be logged.

For high-volume APIs:

```
10,000 requests/sec
```

logging every request at INFO may produce enormous volumes.

Possible strategies:

```
Metrics for Request Rate
Logs for Important Events
DEBUG for Detailed Request Logging
Sampling for High-Volume Events
```

---

# 45. HTTP Request Logging

Example:

```
INFO
method=GET
route=/orders
status=200
duration_ms=25
```

This may be useful, but high-traffic systems should consider the resulting volume.

Metrics can provide aggregate request statistics more efficiently.

---

# 46. HTTP Error Logging

An HTTP error may be logged at ERROR depending on the failure type.

Example:

```
ERROR
method=POST
route=/orders
status=500
duration_ms=800
error=database_timeout
```

However, not every 4xx response is necessarily an application error.

---

# 47. 4xx vs 5xx

4xx responses often indicate client-side problems.

Examples:

```
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
```

5xx responses generally indicate server-side failures.

Examples:

```
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

Logging severity should consider the meaning and expected behavior of the response.

---

# 48. Authentication Logging

Example:

```
INFO Authentication successful
```

Security failure:

```
WARN Authentication failed
```

Repeated suspicious failures may require:

```
WARN
```

or:

```
ERROR
```

depending on the security policy and operational significance.

Never log passwords or authentication tokens.

---

# 49. Authorization Logging

Example:

```
WARN Authorization denied
user_role=developer
resource=production-database
```

This can be useful for security investigation.

Avoid logging sensitive identity information unnecessarily.

---

# 50. Retry Logging

Example:

```
WARN External API request failed
retry=1
max_retries=3
```

Second attempt:

```
WARN External API request failed
retry=2
max_retries=3
```

Final failure:

```
ERROR External API request failed
retry=3
max_retries=3
```

This clearly communicates escalation.

---

# 51. Fallback Logging

Suppose a service uses a fallback mechanism.

Example:

```
WARN Payment provider unavailable
fallback=secondary-provider
```

This indicates degraded operation without necessarily indicating complete failure.

If the fallback also fails:

```
ERROR Payment processing failed
primary=unavailable
secondary=unavailable
```

---

# 52. Dependency Failure Logging

Example:

```
WARN payment-service response slow
duration_ms=1500
```

If the request fails:

```
ERROR payment-service request failed
error=timeout
```

This distinction helps identify degraded versus failed dependencies.

---

# 53. Database Logging Levels

Normal:

```
INFO Database connection established
```

Potential problem:

```
WARN Connection pool usage at 85%
```

Operation failure:

```
ERROR Database query failed
```

Application cannot start:

```
FATAL Database initialization failed
```

---

# 54. Kubernetes Logging Levels

Application logs may contain:

```
INFO Server started

WARN Configuration fallback used

ERROR Database connection failed

FATAL Application initialization failed
```

Kubernetes itself also generates events and logs, but application log levels are controlled by the application framework.

---

# 55. Container Logging

Containerized applications should generally write logs to:

```
stdout
stderr
```

The container platform or node-level logging agent can collect them.

Example:

```
Application
    |
    ↓
stdout
    |
    ↓
Container Runtime
    |
    ↓
Fluent Bit
    |
    ↓
Elasticsearch
```

---

# 56. stderr and ERROR Logs

Many applications write errors to:

```
stderr
```

and normal output to:

```
stdout
```

This can make collection easier.

However, the exact behavior depends on the application runtime and logging framework.

---

# 57. Log Level and Metrics

Log levels should not replace metrics.

Example:

```
ERROR Payment failed
```

This tells us an individual operation failed.

A metric:

```
payment_failures_total
```

can tell us:

```
10 failures/minute
```

Metrics are better for aggregation and alerting.

---

# 58. Log Level and Tracing

Logs provide event details.

Traces provide request flow.

Example:

```
ERROR payment-service timeout
trace_id=abc123
```

The trace can show:

```
Order Service
    |
    ↓
Payment Service
    |
    ↓
Database
```

This gives both detailed context and request flow.

---

# 59. Log Levels and Alerting

Not every ERROR should automatically create an alert.

Example:

```
ERROR one request failed
```

may not require immediate human action.

But:

```
ERROR rate > 10%
```

may require an alert.

Alerts should generally be based on meaningful operational signals, often metrics, rather than simply counting log severity.

---

# 60. ERROR Logs vs Error Rate

Suppose:

```
1 ERROR/minute
```

This may be normal.

But:

```
1,000 ERROR/minute
```

may indicate an incident.

Therefore:

```
Log Level
    +
Frequency
    +
Context
```

determines operational importance.

---

# 61. WARN Logs vs Warning Rate

Similarly:

```
One WARN
```

may be harmless.

But:

```
10,000 WARN/minute
```

could indicate a serious issue.

Log volume and rate are important monitoring signals.

---

# 62. Log Level Cardinality

Log level itself is usually low cardinality.

Example:

```
INFO
WARN
ERROR
```

This is good for aggregation.

Avoid creating dynamic log-level-like labels with arbitrary values.

---

# 63. Consistent Log Levels

All services should follow similar definitions.

For example:

```
INFO = Normal Operation

WARN = Degraded / Unexpected but Recoverable

ERROR = Operation Failed

FATAL = Application Cannot Continue
```

Without a common definition, one team's WARN may be another team's ERROR.

---

# 64. Logging Standard

A platform team can define a standard:

```
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

Then document:

```
When to Use Each Level
Examples
Production Defaults
Sensitive Data Rules
Alerting Rules
```

This creates consistency across microservices.

```

```

---

# 71. Log Level Naming

Use consistent naming in structured logs.

Example:

```
level=INFO

level=WARN

level=ERROR
```

Avoid arbitrary variations:

```
level=bad

level=problem

level=important
```

Standardized levels make aggregation and filtering predictable.

---

# 72. Log Level Case

Choose a consistent format:

```
INFO
WARN
ERROR
```

or:

```
info
warn
error
```

The important point is consistency across services.

---

# 73. Log Level and Message Quality

Bad:

```
ERROR Error
```

Better:

```
ERROR Database connection failed
```

Best:

```
ERROR Database connection failed
service=order-service
operation=create_order
dependency=postgres
error=timeout
```

Severity and context should work together.

---

# 74. Avoid Duplicate Errors

A single failure may be logged at multiple layers.

Example:

```
Database Layer:
ERROR Database timeout

Service Layer:
ERROR Order creation failed

Controller:
ERROR Request failed
```

One underlying error can produce three ERROR logs.

This creates noise.

Teams should define where errors are logged and how they propagate.

---

# 75. Exception Propagation

A common strategy:

```
Lower Layer
    |
    ↓
Add Context
    |
    ↓
Propagate Exception
    |
    ↓
Boundary Layer
    |
    ↓
Log Once
```

This can reduce duplicate stack traces.

The correct strategy depends on the application's architecture.

---

# 76. Duplicate Stack Traces

Avoid logging the same stack trace repeatedly.

Bad:

```
Database Layer:
ERROR + Stack Trace

Service Layer:
ERROR + Same Stack Trace

Controller:
ERROR + Same Stack Trace
```

This can dramatically increase log volume.

---

# 77. Log Level and Retry Behavior

Retries require careful severity selection.

Example:

```
Attempt 1 failed:
DEBUG

Attempt 2 failed:
WARN

Final attempt failed:
ERROR
```

This is one possible strategy.

The exact levels depend on how significant the failure is.

---

# 78. Log Level and Circuit Breakers

Example:

```
Circuit closed:
DEBUG

Circuit opened:
WARN

Requests rejected:
WARN

Recovery:
INFO
```

This gives useful operational visibility without logging every internal state check.

---

# 79. Log Level and Cache

Example:

```
Cache hit:
DEBUG

Cache miss:
DEBUG

Cache unavailable:
WARN

Critical cache failure affecting requests:
ERROR
```

Routine cache operations generally should not create large INFO volumes.

---

# 80. Log Level and Health Checks

Example:

```
Successful health check:
DEBUG

Health check degraded:
WARN

Health check failed:
ERROR
```

However, if a health check is expected to fail during certain lifecycle states, the level should reflect that expected behavior.

---

# 81. Log Level and Scheduled Jobs

Example:

```
INFO Job started

INFO Job completed

WARN Job delayed

ERROR Job failed

FATAL Job cannot initialize required scheduler
```

This gives useful operational visibility.

---

# 82. Log Level and Batch Processing

For large batch jobs:

```
INFO Batch started
INFO Batch completed
```

Potential problem:

```
WARN Processing slower than expected
```

Failure:

```
ERROR Batch processing failed
```

Detailed item-level processing:

```
DEBUG
```

This prevents enormous INFO volumes.

---

# 83. Log Level and Deployment

Example:

```
INFO Deployment started

INFO New version initialized

WARN Pod startup taking longer than expected

ERROR Deployment health check failed

FATAL Application cannot initialize
```

Deployment systems can also provide separate deployment events and metrics.

---

# 84. Log Level and Rollback

Example:

```
WARN Error rate increased after deployment

ERROR Deployment validation failed

INFO Rollback started

INFO Rollback completed
```

This sequence provides a useful incident timeline.

---

# 85. Log Level and Configuration

Example:

```
INFO Configuration loaded

WARN Optional configuration missing; using default

ERROR Invalid configuration value

FATAL Required configuration missing
```

This severity model clearly communicates impact.

---

# 86. Log Level and External APIs

Example:

```
DEBUG Sending request to external API

WARN External API response slow

ERROR External API request failed

INFO External API recovered
```

This creates a useful operational timeline.

---

# 87. Log Level and Database Connection Pool

Example:

```
DEBUG Connection acquired

WARN Connection pool usage above 80%

ERROR Connection acquisition timeout

FATAL Database unavailable during application initialization
```

This helps differentiate normal activity from degraded operation.

---

# 88. Log Level and Kubernetes Probes

Example:

```
DEBUG Readiness probe succeeded

WARN Readiness probe delayed

ERROR Readiness probe failed
```

But successful probes should generally not be logged at INFO for high-frequency production workloads.

---

# 89. Log Level and Autoscaling

Example:

```
INFO Scaling triggered

DEBUG HPA evaluation details

WARN Desired replicas cannot be reached

ERROR Autoscaling operation failed
```

Metrics should remain the primary source for capacity and scaling analysis.

---

# 90. Log Level and Security Events

Example:

```
INFO Successful authentication

WARN Failed authentication

WARN Authorization denied

ERROR Security control failure

FATAL Security subsystem cannot initialize
```

Security teams may use different severity definitions depending on policy.

---

# 91. Log Level and Audit Events

Audit events may use INFO or a dedicated audit category.

Example:

```
INFO user_role_changed

INFO production_deployment_approved
```

The important requirement is that audit events are reliably captured and protected.

---

# 92. Log Level and Sensitive Data

Never assume that DEBUG is safe for sensitive information.

A developer may accidentally log:

```
DEBUG request_body={...}
```

If the request contains:

```
password
token
credit_card
```

the sensitive data may be exposed.

Log-level changes should therefore be reviewed carefully.

---

# 93. Production Debugging Risks

Temporarily enabling DEBUG can expose:

```
Request Payloads
Headers
Tokens
User Information
Database Queries
```

Before enabling DEBUG in production:

```
Review Logging Configuration
Check Sensitive Fields
Enable Only Required Components
Disable After Investigation
```

---

# 94. Log Level Changes as Operational Changes

Changing:

```
INFO → DEBUG
```

can significantly increase log volume.

Treat log-level changes as operational changes.

For production systems:

```
Record Who Changed It
Record Why
Record When
Revert After Investigation
```

# 105. Log Level Best Practices

```
1. Define standard levels.

2. Document the meaning of every level.

3. Use INFO for meaningful normal operations.

4. Use WARN for degraded or potentially problematic behavior.

5. Use ERROR for failed operations.

6. Use FATAL only when the application cannot continue.

7. Use DEBUG for detailed troubleshooting.

8. Use TRACE only when extremely detailed execution information is required.

9. Avoid excessive INFO logging.

10. Avoid permanent DEBUG logging in production.

11. Avoid logging sensitive information.

12. Standardize levels across microservices.

13. Prefer component-level debugging over global DEBUG.

14. Monitor log volume by severity.

15. Correlate log severity with metrics.

16. Avoid duplicate errors and stack traces.

17. Treat production log-level changes as controlled changes.

18. Revert temporary DEBUG changes.

19. Use structured fields consistently.

20. Document language-specific mappings.
```

# 107. Common Mistakes

## Mistake 1: Everything Is INFO

Example:

```
INFO Starting method
INFO Checking variable
INFO Calling database
INFO Cache lookup
INFO Request received
INFO Request completed
```

This creates excessive noise.

Use DEBUG for detailed technical information.

---

# 108. Common Mistake 2: Everything Is ERROR

Example:

```
ERROR Cache miss
ERROR Retry attempt
ERROR User entered invalid password
ERROR 404 Not Found
```

Not every unexpected or unsuccessful event is a server error.

Severity should reflect operational impact.

---

# 109. Common Mistake 3: DEBUG Enabled Permanently

This causes:

```
High Volume
High Cost
More Noise
Possible Sensitive Data Exposure
```

Use DEBUG strategically.

---

# 110. Common Mistake 4: No Consistent Definitions

If:

```
Service A:
WARN = Error
```

and:

```
Service B:
WARN = Normal Retry
```

centralized analysis becomes confusing.

Define a platform-wide standard.

---

# 111. Common Mistake 5: Logging Secrets at DEBUG

Developers may assume DEBUG is only visible internally.

But centralized logs may be accessible by:

```
Developers
Operations
Security Teams
Vendors
Other Systems
```

Never log secrets.

---

# 112. Common Mistake 6: Duplicate Logging

The same exception may be logged multiple times.

This creates:

```
Duplicate Events
Higher Storage
More Noise
```

Define clear ownership of error logging.

---

# 113. Common Mistake 7: Alerting on Every ERROR

One ERROR does not necessarily mean an incident.

Instead consider:

```
Error Rate
Error Percentage
Duration
Impact
User Experience
```

Use metrics and alerting rules to determine operational significance.

---

# 114. Common Mistake 8: Ignoring Log Volume

A service may produce:

```
100 GB/day
```

without anyone noticing until storage costs become significant.

Monitor:

```
Logs/sec
GB/day
Logs by Service
Logs by Level
```

---

# 115. Common Mistake 9: No Temporary Debugging Strategy

If production debugging requires restarting every service or modifying source code, incident response becomes slower.

Applications should ideally provide controlled mechanisms for increasing verbosity for specific components.

---

# 116. Common Mistake 10: No Log-Level Documentation

Developers should know:

```
What to log at INFO
What to log at WARN
What to log at ERROR
What belongs in DEBUG
```

Document this as part of the engineering standard.

# 118. Interview Question: Which Log Level Would You Use for a Database Failure?

The level should reflect the operational impact.

### Answer

# 121. Interview Question: How Would You Debug a Production Issue Without Enabling DEBUG Everywhere?

### Answer

8. Restore the original INFO level.

This minimizes unnecessary log volume.

# 122. Interview Question: What Is the Difference Between WARN and ERROR?

### Answer

WARN generally means something unexpected or degraded happened but the system can continue.

ERROR generally means an operation failed.

Example:

```
WARN External API is slow

ERROR External API request failed
```

# 123. Interview Question: What Is the Difference Between ERROR and FATAL?

### Answer

ERROR usually represents a failed operation or component.

FATAL represents a condition where the application or critical component cannot continue.

Example:

```
ERROR Payment request failed

FATAL Required configuration missing during startup
```

# 133. Final Log-Level Mental Model

Think of log levels as:

```
TRACE
   ↓
"Show me everything"

DEBUG
   ↓
"Help me troubleshoot"

INFO
   ↓
"Tell me important normal events"

WARN
   ↓
"Something unusual or degraded happened"

ERROR
   ↓
"An operation failed"

FATAL
   ↓
"The application cannot continue"
```

The goal is not to produce as many logs as possible.

The goal is to produce the right amount of information at the right severity.

A strong production logging strategy provides:

```
Consistent Severity
    +
Useful Context
    +
Controlled Volume
    +
Sensitive Data Protection
    +
Centralized Collection
    +
Metrics Correlation
    +
Trace Correlation
```

This makes logs useful during normal operations, troubleshooting, security investigations, and production incidents.
