# Interview Preparation

# 01 - Basic Questions

> Monitoring, Observability & Logging — Basic DevOps Interview Preparation

---

# 1. How Do You Define Monitoring?

## What the interviewer is testing

They want to know whether you understand monitoring as more than simply installing a tool.

## Strong answer

> Monitoring is the continuous collection, visualization and evaluation of system health data such as metrics, logs and alerts. It helps us detect failures, performance degradation, resource saturation and availability issues before or while they affect users.

## Detailed explanation

Monitoring helps answer:

    Is the system healthy?
    Is something abnormal?
    When did the problem start?
    Is the system approaching a limit?
    Does an operator need to take action?

Typical monitoring areas:

    Infrastructure
    Applications
    Kubernetes
    Databases
    Networks
    APIs
    Dependencies

## Production example

For an EKS application I would monitor:

    Node CPU/memory
    Pod CPU/memory
    Pod restarts
    Application request rate
    Error rate
    Response latency
    ALB health
    Database health
    Prometheus targets
    Alert status

## Common mistake

> "Monitoring means checking CPU and memory."

That is incomplete.

CPU and memory are only infrastructure signals.

---

# 2. What Is Observability?

## Strong answer

> Observability is the ability to understand the internal state and behavior of a system from the telemetry it produces. The main signals are metrics, logs and traces, supported by context such as metadata, events and deployment information.

## Monitoring vs Observability

Monitoring:

    "The error rate is 20%."

Observability:

    "The error rate increased after deployment version X. The failures are concentrated on the orders service, specifically the payment dependency, and logs show connection timeout errors."

Monitoring detects.

Observability helps investigate.

## Interview point

Do not say that observability is simply "more monitoring."

It is about being able to explain system behavior.

## Strong answer

The traditional three pillars are:

    Metrics
    Logs
    Traces

## Metrics

Numerical measurements over time.

Examples:

    CPU usage
    Request rate
    Error rate
    Request latency

## Logs

Detailed event records.

Examples:

    Application errors
    Authentication events
    Deployment messages
    Exceptions

## Traces

Track a request across distributed services.

Example:

    ALB
      |
      v
    Order Service
      |
      v
    Payment Service
      |
      v
    Database

## Important point

Modern observability can also include:

    Profiles
    Events
    Deployment metadata
    Continuous profiling

But metrics, logs and traces remain the core signals.

# 4. What Is a Metric?

## Strong answer

> A metric is a numerical measurement of a system or application behavior collected over time.

Examples:

    http_requests_total
    process_cpu_seconds_total
    node_memory_MemAvailable_bytes

A metric normally has:

    Name
    Value
    Timestamp
    Labels

Example:

    http_requests_total{
      service="orders",
      method="GET",
      status="200"
    }

# 5. What Is a Log?

## Strong answer

> A log is a timestamped record of an event generated by an application, system or infrastructure component.

Example:

    2026-08-15T10:10:20Z
    service=orders
    level=ERROR
    status=500
    message="payment timeout"

Logs are useful for detailed investigation.

# 6. What Is a Trace?

## Strong answer

> A trace represents the journey of a request through one or more services in a distributed system. It is composed of spans that represent individual operations.

Example:

    Trace
      |
      +-- ALB
      |
      +-- Order Service
      |
      +-- Payment Service
      |
      +-- Database

This helps identify where latency or failures occur.

# 7. What Are the Golden Signals?

The four Golden Signals are:

    Latency
    Traffic
    Errors
    Saturation

## Latency

How long requests take.

## Traffic

How much demand the system receives.

## Errors

How many requests fail.

## Saturation

How close a resource is to its capacity.

## Example

For an API:

    Traffic:
    2,000 requests/sec

    Latency:
    p95 = 250 ms

    Errors:
    1.2%

    Saturation:
    CPU = 85%

# 10. What Is Prometheus?

## Strong answer

> Prometheus is an open-source monitoring and time-series database platform designed primarily for collecting and querying metrics. It commonly uses a pull-based model where Prometheus scrapes HTTP metrics endpoints.

Key components:

    Exporters

    PromQL

# 12. Why Is Prometheus Pull-Based?

## Strong answer

> Prometheus normally discovers targets and pulls metrics from them at configured intervals. This makes target health visible through scrape status and allows Prometheus to control collection frequency.

Advantages:

    Simple model
    Target health visibility
    Centralized scraping configuration
    Easy service discovery

# 15. What Is PromQL?

## Strong answer

> PromQL is Prometheus's query language. It is used to select, filter, aggregate and calculate values from time-series metrics.

Example:

    up

Returns target availability.

Example:

    rate(http_requests_total[5m])

Calculates the per-second request rate over five minutes.

# 16. What Is a Label in Prometheus?

A label adds dimensions to a metric.

Example:

    http_requests_total{
      service="orders",
      method="GET",
      status="500"
    }

Labels allow filtering and aggregation.

Example:

    sum by (service) (
      rate(http_requests_total[5m])
    )

---

# 17. What Is Cardinality?

## Strong answer

> Cardinality is the number of unique time-series combinations created by metric labels.

For example:

    service
    method
    status

may have bounded values.

Dangerous labels:

    user_id
    request_id
    session_id

These can create enormous numbers of unique series.

---

# 18. Why Is High Cardinality Dangerous?

High cardinality increases:

    Memory
    CPU
    Storage
    Query cost
    Network traffic
    Remote storage cost

Example:

    http_requests_total{
      request_id="unique-value"
    }

Every request may create a new series.

Better:

    Put request_id in logs.

# 23. What Is Alertmanager?

## Strong answer

> Alertmanager handles alerts generated by Prometheus. It provides grouping, deduplication, routing, silencing and inhibition before notifications are sent to receivers.

# 24. What Is Alert Grouping?

Suppose one node fails and causes:

    50 pod alerts

Without grouping:

    50 notifications

With grouping:

    Node failure
       |
       +-- related pod alerts

This reduces notification noise.

---

# 25. What Is Alert Inhibition?

Inhibition suppresses lower-priority alerts when a higher-level root-cause alert is active.

Example:

    Database DOWN
       |
       +-- Order service failing
       +-- Payment service failing
       +-- Inventory service failing

Instead of paging for everything, the database failure can suppress dependent alerts.

# 26. What Is Alert Fatigue?

Alert fatigue occurs when engineers receive too many alerts.

Consequences:

    Important alerts ignored
    Slower response
    Engineers silence notifications
    On-call burnout

Good alerts should be:

    Actionable
    Relevant
    Owned
    Prioritized

# 39. What Does CrashLoopBackOff Mean?

## Strong answer

> CrashLoopBackOff means a container repeatedly starts, crashes and Kubernetes backs off before restarting it again.

Common causes:

    Application crash
    Bad configuration
    Missing environment variable
    Missing secret
    Dependency failure
    Incorrect command
    Liveness probe failure
    Resource issue

---

# 40. How Do You Troubleshoot CrashLoopBackOff?

Use:

    kubectl get pod <pod>
    kubectl describe pod <pod>
    kubectl logs <pod>
    kubectl logs <pod> --previous

Then check:

    Events
    Exit code
    Previous logs
    Environment variables
    Secrets
    ConfigMaps
    Probes
    Resource limits

---

# 41. What Does OOMKilled Mean?

OOMKilled means the container was terminated because it exceeded its memory limit or the node experienced memory pressure leading to an OOM condition.

Check:

    kubectl describe pod <pod>

Look for:

    Reason: OOMKilled

Then investigate:

    Memory limit
    Actual usage
    Application memory behavior
    Recent deployment
    Traffic increase

Do not blindly increase memory without understanding the cause.

---

# 42. What Is a Readiness Probe?

Readiness determines whether a pod should receive traffic.

If readiness fails:

    Pod remains running
    But should not receive traffic through the service

Use it for:

    Application startup
    Dependency readiness
    Traffic acceptance

---

# 43. What Is a Liveness Probe?

Liveness determines whether the container is considered unhealthy enough to restart.

If liveness fails repeatedly:

    Kubernetes may restart the container.

Be careful:

> A poorly designed liveness probe can cause restart loops.

---

# 44. Readiness vs Liveness

| Readiness | Liveness |
|---|---|
| Can receive traffic? | Is the container alive? |
| Removes pod from service endpoints | Can trigger restart |
| Protects traffic routing | Recovers stuck processes |
| Should not normally restart app | Can restart app |

# 45. What Is SLI?

SLI = Service Level Indicator.

It is the actual measurement of service behavior.

Examples:

    Successful request percentage
    p95 latency
    Availability

Example:

    Successful requests / total valid requests

---

# 46. What Is SLO?

SLO = Service Level Objective.

It is the target for an SLI.

Example:

    SLI:
    Availability

    SLO:
    99.9% monthly availability

The SLO should represent an actual reliability objective.

---

# 47. What Is SLA?

SLA = Service Level Agreement.

It is a contractual/business commitment.

Difference:

    SLI = measurement
    SLO = target
    SLA = contractual commitment

---

# 48. What Is an Error Budget?

If the SLO is:

    99.9%

then allowed failure is:

    0.1%

That allowed unreliability is the error budget.

It helps teams balance:

    Reliability
    Feature delivery

# 50. What Is Monitoring vs Tracing?

Monitoring:

    Detects aggregate behavior.

Tracing:

    Follows individual requests.

Example:

    Metric:
    p95 latency = 2 sec

    Trace:
    Order Service = 200 ms
    Payment Service = 1.6 sec
    Database = 100 ms

Tracing identifies where latency is occurring.

# 51. Why Are Metrics Usually Better Than Logs for Alerting?

    Efficient to query

    More processing
    More storage
    More query cost

Logs are still valuable for investigation.

# 54. What Is Scrape Interval?

Scrape interval determines how frequently Prometheus collects metrics.

Example:

    scrape_interval: 30s

means Prometheus attempts to scrape targets every 30 seconds.

Shorter intervals:

    Faster detection
    More samples
    More resource consumption

Choose based on requirements.

---

# 55. What Is Scrape Timeout?

Scrape timeout defines how long Prometheus waits for a target response.

If timeout is too short:

    Valid targets may appear unhealthy.

If too long:

    Slow targets can consume resources.

It should normally be less than the scrape interval.

---

# 56. What Does `up == 0` Mean?

`up` is a Prometheus-generated metric indicating scrape success.

Typical interpretation:

    up == 1
    Target scrape succeeded

    up == 0
    Target scrape failed

It does not automatically mean:

> The application itself is completely down.

The metrics endpoint or network path may be the problem.

# 68. What Is Backpressure?

Backpressure occurs when:

    Producer rate > Consumer rate

Example:

    Application:
    100,000 logs/sec

    Backend:
    60,000 logs/sec

The remaining events accumulate in a queue.

If the mismatch continues:

    Queue fills
       |
       v
    Data loss / failure

---

# 86. How Would You Monitor an EKS Microservices Application?

## Strong answer

> I would monitor EKS at multiple layers. At the infrastructure layer I would monitor nodes, CPU, memory, filesystem and network. At the Kubernetes layer I would monitor pods, restarts, OOMKilled, readiness/liveness and cluster capacity. At the application layer I would monitor RED metrics such as request rate, errors and latency. Prometheus would collect metrics, Grafana would provide dashboards, and ELK would provide centralized application logging. Alerts would be designed around user impact and SLOs.

# 109. Basic Interview Question — What Is the Difference Between p50, p95 and p99?

Percentiles describe distribution.

Example:

    p50 = 100 ms
    p95 = 300 ms
    p99 = 800 ms

Interpretation:

    50% of requests are at or below p50
    95% are at or below p95
    99% are at or below p99

Higher percentiles reveal tail latency.

---

# 110. Why Is p95 Often More Useful Than Average Latency?

Average can hide slow requests.

Example:

    99 requests = 100 ms
    1 request = 10 seconds

Average may not represent the experience of the slow request.

p95/p99 expose tail behavior better.

# 116. Why Is Pushgateway Not a General Metrics Gateway?

Pushgateway can cause stale metrics to remain if lifecycle management is poor.

It is primarily intended for:

    Short-lived batch jobs

not:

    Every long-running application

For long-running services, normal Prometheus scraping is generally preferable.

# 134. Key Basic Interview Takeaways

> Prometheus is primarily a pull-based metrics system.

> PromQL is used to query and analyze Prometheus metrics.

> Grafana visualizes data and provides dashboards.

> ELK centralizes and analyzes logs.

> Metrics are excellent for detection and alerting.

> Logs provide detailed diagnostic context.

> Traces show request flow across distributed services.

> High-cardinality labels are a major Prometheus risk.

> Kubernetes monitoring must cover nodes, pods, workloads and applications.

> Good alerts are actionable, owned and prioritized.

> SLI is the measurement, SLO is the target, and SLA is the contractual commitment.

> Observability itself must be monitored.

> Production troubleshooting should correlate metrics, logs, Kubernetes state, dependencies and recent changes.

> A strong DevOps engineer does not just know the tools — they know how to use telemetry to operate production systems.
