# Kubernetes Logging

## 1. Overview

Kubernetes logging is the process of collecting, centralizing, storing, searching, and analyzing logs generated by applications, containers, Pods, Nodes, and Kubernetes components.

A production Kubernetes environment can generate logs from multiple layers:

```text
Kubernetes Logging
│
├── Application Logs
├── Container Logs
├── Pod Logs
├── Node Logs
├── Kubernetes Component Logs
├── Ingress / Load Balancer Logs
└── Infrastructure Logs
```

A typical centralized logging architecture is:

```text
Applications
     ↓
Containers
     ↓
Container Runtime
     ↓
Node Log Files
     ↓
Logging Agent
     ↓
Log Processing
     ↓
Centralized Log Storage
     ↓
Kibana / Visualization
```

---

# 2. Why Kubernetes Logging Is Important

Kubernetes monitoring tells us that something is wrong.

Logs help explain what happened.

For example:

```text
Metric:
HTTP 5xx increased
       ↓
Log:
Database connection timeout
       ↓
Root Cause:
Database dependency unavailable
```

Logging helps with:

```text
Troubleshooting
Root-cause analysis
Application debugging
Security investigation
Incident response
Audit requirements
Performance analysis
```

---

# 4. Container Logging

Applications running inside containers should normally write logs to:

```text
stdout
stderr
```

Example:

```bash
echo "Application started"
```

Kubernetes/container runtime captures the output.

Conceptually:

```text
Application
    ↓
stdout / stderr
    ↓
Container Runtime
    ↓
Kubernetes logging
```

---

# 5. Why stdout and stderr?

Containerized applications should avoid relying on local application log files inside the container filesystem.

Instead:

```text
Application
    ↓
stdout / stderr
    ↓
Container runtime
    ↓
Logging agent
```

Advantages include:

```text
Centralized collection
Simple container lifecycle
No dependency on application filesystem
Easy log aggregation
```

---

# 6. Viewing Pod Logs

The basic command is:

```bash
kubectl logs <pod-name>
```

Example:

```bash
kubectl logs payment-7d9f8c
```

For a namespace:

```bash
kubectl logs payment-7d9f8c -n production
```

This is useful for immediate troubleshooting.

---

# 7. Following Logs

To continuously follow logs:

```bash
kubectl logs -f <pod-name>
```

Example:

```bash
kubectl logs -f payment-7d9f8c -n production
```

This is useful when reproducing an issue or watching an application during deployment.

---

# 8. Previous Container Logs

If a container has restarted, the current container may not contain the logs from the previous instance.

Use:

```bash
kubectl logs <pod-name> --previous
```

Example:

```bash
kubectl logs payment-7d9f8c --previous -n production
```

This is especially useful for:

```text
CrashLoopBackOff
OOMKilled
Application crashes
Probe failures
```

---

# 9. Multi-Container Pods

A Pod can contain multiple containers.

Example:

```text
Pod
├── application
└── sidecar
```

To specify a container:

```bash
kubectl logs <pod-name> -c <container-name>
```

Example:

```bash
kubectl logs orders-7d9f8c -c application
```

For a sidecar:

```bash
kubectl logs orders-7d9f8c -c sidecar
```

---

# 10. Previous Logs From a Specific Container

For a restarted container:

```bash
kubectl logs <pod-name> \
  -c <container-name> \
  --previous
```

This can help identify the reason for the previous container termination.

---

# 11. Logs From All Pods

For a Deployment or multiple Pods, you may need to inspect logs across replicas.

Example:

```text
orders
├── orders-1
├── orders-2
└── orders-3
```

A centralized logging system is much more practical than manually running:

```bash
kubectl logs
```

against every Pod.

---

# 12. Why Centralized Logging?

Kubernetes workloads are dynamic.

Pods can:

```text
Start
Stop
Restart
Scale
Move between Nodes
```

If logs remain only on individual Nodes:

```text
Node-1 → Logs
Node-2 → Logs
Node-3 → Logs
```

investigation becomes difficult.

Centralized logging provides:

```text
All logs
    ↓
One searchable platform
```

---

In this architecture:

```text

Kibana        → Visualization
```

# 14. Logging Agent

A logging agent runs close to the workloads.

In Kubernetes, it is commonly deployed as a DaemonSet.

```text
Node-1 → Logging Agent
Node-2 → Logging Agent
Node-3 → Logging Agent
```

Each agent collects logs from its Node.

Architecture:

```text
Node
├── Application Pods
├── Container Runtime
├── Log Files
└── Logging Agent
```

---

# 15. Why DaemonSet?

A DaemonSet ensures that the logging agent runs on the required Nodes.

Example:

```text
10 Nodes
   ↓
10 Logging Agent Pods
```

When a new Node is added:

```text
New Node
   ↓
DaemonSet
   ↓
Logging Agent automatically scheduled
```

This makes it suitable for node-level log collection.

# 17. Container Runtime Logs

The container runtime stores container output on the Node.

The logging agent reads these logs and forwards them.

Conceptually:

```text
Container
    ↓
stdout
    ↓
Runtime
    ↓
Node log file
    ↓
Agent
```

The agent should track log positions so that it can continue collecting after restarts.

# 18. Log Rotation

Applications can generate large amounts of logs.

Without rotation:

```text
Log file
   ↓
Growing continuously
   ↓
Disk fills
   ↓
DiskPressure
```

Log rotation prevents a single log file from consuming unlimited disk space.

Production logging must consider:

```text
Log size
Rotation
Retention
Compression
Disk usage
```

---

# 19. Node Disk Pressure From Logs

Example:

```text
Application logs
      ↓
Large log volume
      ↓
Node filesystem fills
      ↓
DiskPressure
      ↓

```

Therefore, logging is also a Kubernetes capacity concern.

Monitor:

```text
Node filesystem
Container logs
Ephemeral storage
DiskPressure
```

# 20. Structured Logging

Prefer structured logs instead of unstructured text.

Unstructured:

```text
Payment failed for order 1234
```

Structured:

```json
{
  "level": "ERROR",
  "service": "payment",
  "message": "Payment failed",
  "order_id": "1234"
}
```

Structured logs are easier to:

```text
Search
Filter
Aggregate
Parse
Analyze
```

---

A centralized logging pipeline can parse these fields automatically.

# 40. Why Not Run Logstash as a DaemonSet?

Logstash is generally heavier than a lightweight node-level logging agent.

A common architecture is:

```text
Node
 ↓
Lightweight Agent
 ↓
Central Logstash
 ↓
Elasticsearch
```

This separates:

```text
Collection
from
Processing
```

and allows Logstash to scale independently.

---

# 41. Log Collection Resilience

Suppose Logstash becomes temporarily unavailable.

```text
Agent
  ↓
Logstash
  X
```

A production agent should have appropriate buffering or queueing where supported.

This helps prevent immediate loss of logs during short interruptions.

However, buffers should be bounded to avoid consuming unlimited Node resources.

# 48. Log Sampling

For extremely high-volume workloads, organizations may reduce:


# 50. Sensitive Data

Never intentionally log:

```text
Passwords
Access tokens
Secret keys
Authorization headers
Credit card information
Sensitive personal information
```

Bad:

```json
{
  "username": "user",
  "password": "secret123"
}
```

Better:

```json
{
  "username": "user",
  "authentication": "successful"
}
```


But filtering should not replace secure application logging practices.

```text

```

**Not every Kubernetes failure produces application logs.**

# 71. Logging for OOMKilled

If a container is OOMKilled, application logs may not show the complete reason because the process can be terminated abruptly.

```text

Pod status
+

+
```

```text

     ↓

```

# 72. Logging and Ephemeral Containers

For difficult debugging scenarios, ephemeral containers can sometimes be used to inspect a running Pod.

Logging should remain the primary source of historical application information.

# 97. Interview Question

### How does Kubernetes logging work?

**Answer:**

Applications running in containers commonly write logs to stdout and stderr. The container runtime captures those logs and stores them on the Node. A node-level logging agent, commonly deployed as a DaemonSet, collects the logs and forwards them to a centralized logging pipeline such as Logstash and Elasticsearch. Kibana provides search and visualization. For production, I also monitor the logging pipeline itself and correlate logs with Prometheus metrics and Jaeger traces.

---

# 98. Interview Question

### Why do you use a DaemonSet for log collection?

**Answer:**

A DaemonSet ensures that a logging agent runs on the required Kubernetes Nodes. The agent can collect container logs locally from each Node. When a new Node is added, Kubernetes automatically schedules the DaemonSet Pod there, making it suitable for cluster-wide node-level log collection.

# 100. Interview Question

### How do you handle high log volume?

**Answer:**

I first identify which applications and log types are generating the volume. Then I review log levels, filter unnecessary health-check or repetitive logs, use structured logging, configure appropriate retention and lifecycle policies, and scale the logging pipeline when required. I also monitor ingestion rate and backlog to ensure the logging infrastructure can keep up.

---

# 101. Interview Question

### How do you prevent logs from filling Kubernetes Nodes?

**Answer:**

I monitor Node filesystem and ephemeral storage usage, configure appropriate container log rotation, control application log volume, filter unnecessary logs, and ensure the logging pipeline can process logs at the expected rate. I also monitor DiskPressure and investigate applications generating abnormal log volumes.

---

# 102. Interview Question

### How do you secure Kubernetes logs?

**Answer:**

I prevent applications from logging secrets or sensitive information, use secure communication between logging components where required, restrict access through authentication and authorization, use least-privilege RBAC, keep logging infrastructure on private network paths where practical, and apply appropriate retention and access policies.

---

# 103. Interview Question

### How do you correlate logs with traces?

**Answer:**

I include a trace ID in structured application logs. When an incident occurs, I can search Kibana using the trace ID and then use the same trace ID in Jaeger to inspect the distributed request. This allows me to move from the application log to the exact trace and identify which service or dependency caused the problem.

---

# 104. Interview Question

### What would you monitor in a production logging pipeline?

**Answer:**

I would monitor logging agent availability, input and output rates, dropped events, buffers, connection errors, Logstash pipeline throughput, queue size, Elasticsearch indexing rate, cluster health, disk utilization, JVM pressure, search latency, and Kibana availability. The goal is to detect both log loss and logging infrastructure degradation.


```text

         Metrics             Logs             Traces
```

The key principle is:

**Kubernetes logging should provide reliable, centralized, searchable access to application and infrastructure logs while remaining scalable, secure, and observable itself. In production, logging must also address rotation, retention, storage capacity, backpressure, sensitive-data protection, access control, and correlation with Prometheus metrics and Jaeger traces.**
