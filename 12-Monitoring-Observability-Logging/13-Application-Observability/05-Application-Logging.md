# Application Logging

## 1. Overview

Application logging is the practice of recording important events, errors, warnings, and operational information generated by an application.

Logs help engineers understand:

```text
What happened?
When did it happen?
Which service was affected?
Which request was involved?
What error occurred?
Which dependency failed?
Which application version was running?
```

In production, logs are one of the primary observability signals alongside:

```text
Metrics
Logs
Traces
```

---

# 2. Why Application Logging Matters

Metrics can tell us:

```text
Error rate increased
Latency increased
CPU increased
```

But logs can provide the details:

```text
Database connection timeout
Payment API returned HTTP 503
Invalid configuration
Authentication failed
Application exception
```

Therefore:

```text
Metrics
   ↓
Detect Problem
   ↓
Logs
   ↓
Understand Problem
   ↓
Traces
   ↓
Locate Root Cause
```

---

# 5. Application Logs

Application logs describe what the application is doing.

Example:

```text
User service started
Order created
Payment request initiated
Inventory updated
```

Example structured log:

```json
{
  "level": "INFO",
  "service": "order-service",
  "message": "Order created",
  "order_id": "12345"
}
```

---

# 6. Access Logs

Access logs record incoming HTTP requests.

Example:

```text
2026-08-11T09:30:00Z
GET /api/products
200
145ms
```

Useful fields:

```text
HTTP method
Path
Status code
Response time
Client information
Request ID
```

Access logs are useful for analyzing traffic and API behavior.

---

# 7. Error Logs

Error logs capture failures.

Example:

```text
ERROR Database connection timeout
```

A useful error log should contain enough context to investigate the failure.

Example:

```json
{
  "level": "ERROR",
  "service": "payment-service",
  "error": "Database connection timeout",
  "endpoint": "/payments",
  "request_id": "abc123"
}
```

---

# 8. Warning Logs

Warnings indicate unusual behavior that may not currently be a failure.

Examples:

```text
Connection pool nearly exhausted
Cache hit ratio decreased
Retry count increased
Configuration approaching limit
```

Example:

```json
{
  "level": "WARN",
  "service": "order-service",
  "message": "Database connection pool utilization is high"
}
```

---

# 9. Informational Logs

INFO logs describe important application events.

Examples:

```text
Application started
Configuration loaded
Database connection established
Order processed
Worker started
```

Avoid logging every minor internal operation at INFO level in high-volume production systems.

---

# 10. Debug Logs

DEBUG logs provide detailed troubleshooting information.

Examples:

```text
Request payload processed
Database query execution details
Internal function execution
Cache lookup
```

DEBUG logging can generate large volumes of data.

Therefore:

```text
Production
→ INFO/WARN/ERROR

Troubleshooting
→ Temporarily enable DEBUG when appropriate
```

---

# 11. Critical Logs

Critical logs indicate severe conditions requiring immediate attention.

Examples:

```text
Application cannot start
Database unavailable
Critical configuration missing
Security subsystem failure
Persistent dependency failure
```

Example:

```json
{
  "level": "CRITICAL",
  "service": "payment-service",
  "message": "Unable to initialize database connection"
}
```

---

# 12. Log Levels

A common hierarchy is:

```text
DEBUG
  ↓
INFO
  ↓
WARN
  ↓
ERROR
  ↓
CRITICAL
```

The exact names depend on the logging framework.

The important principle is to use log levels consistently.

---

# 13. Structured Logging

Structured logging stores log information as fields instead of only plain text.

Plain text:

```text
Payment failed for order 12345
```

Structured:

```json
{
  "timestamp": "2026-08-11T09:30:00Z",
  "level": "ERROR",
  "service": "payment",
  "environment": "production",
  "message": "Payment failed",
  "order_id": "12345"
}
```

Structured logs are easier to search, filter, aggregate, and analyze.

---

# 14. Why JSON Logs Are Useful

JSON logs provide consistent fields.

Example:

```json
{
  "service": "inventory",
  "level": "ERROR",
  "status": 500,
  "latency_ms": 1200,
  "message": "Database timeout"
}
```

Kibana can search specific fields:

```text
service = inventory
status = 500
level = ERROR
```

This is much easier than parsing inconsistent plain-text messages.

# 16. Timestamp

Every log should contain a timestamp.

Example:

```json
{
  "timestamp": "2026-08-11T09:30:00.123Z",
  "message": "Payment request started"
}
```

Use a consistent format such as ISO 8601.

Accurate timestamps are essential when correlating:

```text
Metrics
Logs
Traces
```

Always identify which service generated the log.

Example:


```text

Order Service
```

Include the environment when useful.

Example:


Possible values:


Include the application version or release identifier.

Example:


# 20. Request ID

A Request ID identifies a specific incoming request.

Example:

```text
Request ID:
req-123456
```

Logs associated with the request can contain:

```json
{
  "request_id": "req-123456"
}
```

Then engineers can search all logs related to that request.

---

# 21. Trace ID

A Trace ID identifies a distributed request across services.

Example:

```text
Trace ID:
abc123
```

Multiple services can produce logs containing:

```text
trace_id=abc123
```

This allows engineers to connect:

```text
Frontend
   ↓
Order Service
   ↓
Payment Service
   ↓
Database
```

---

# 22. Span ID

A Span ID identifies one operation inside a trace.

Example:

```text
Trace ID = abc123

Order Service
  Span = 111

Payment Service
  Span = 222

Database
  Span = 333
```

This allows logs to be correlated with specific trace operations.

# 44. Logging Sensitive Data

Never log secrets.

Avoid:

```text
Passwords
Access tokens
Private keys
API keys
Database credentials
Session tokens
Sensitive personal information
```

Bad:

```json
{
  "password": "secret123"
}
```

Good:

```json
{
  "message": "Authentication failed",
  "user_id": "12345"
}
```

Only include the minimum information required for troubleshooting.

# 45. Log Volume

Excessive logging can create:

```text
High storage usage
Higher Elasticsearch cost
Higher network traffic
Slower searches
More noise
```

Therefore:

```text
Log everything useful
≠
Log everything possible
```

Focus on actionable information.

# 70. Interview Question

### Why is application logging important?

**Answer:**

Application logging provides detailed information about what happened inside a service. Metrics can tell me that error rate or latency increased, but logs can show the exact exception, dependency failure, request, or configuration problem. In production I use structured centralized logs and correlate them with metrics and traces for faster root-cause analysis.

---

# 71. Interview Question

### What is structured logging?

**Answer:**

Structured logging records log events as consistent fields, commonly JSON, instead of only plain text. Fields such as timestamp, service, environment, log level, request ID, trace ID, status code, and error type make logs easier to search, filter, aggregate, and analyze in systems such as Elasticsearch and Kibana.

---

# 72. Interview Question

### Why should we include Trace ID in application logs?

**Answer:**

A Trace ID allows logs generated by different services during the same distributed request to be correlated. For example, if a request travels through Order, Payment, and Inventory services, all related logs can contain the same Trace ID. This allows engineers to move from a trace to the exact logs associated with the request.

---

# 73. Interview Question

### How would you troubleshoot a Pod that restarted?

**Answer:**

I would first check the Pod status and events using `kubectl describe pod`. Then I would inspect the current and previous container logs using `kubectl logs` and `kubectl logs --previous`. I would check whether the container was OOMKilled, whether the application crashed, whether there was a failed health probe, and whether a recent deployment or configuration change caused the restart.

# 74. Interview Question

### How would you troubleshoot a sudden increase in HTTP 500 errors?

**Answer:**

I would first check the error rate and identify the affected service and endpoint. Then I would search centralized logs for HTTP 500 responses and exceptions. I would correlate the errors with recent deployments, database failures, external dependencies, and traces. If the issue started immediately after a deployment, I would evaluate rollback while continuing root-cause analysis.

# 75. Interview Question

### How do you design logging for microservices?

**Answer:**

I would use a consistent structured logging format across all services. Each log should contain fields such as timestamp, service, environment, version, log level, request ID, trace ID, status code, and error information where applicable. Logs would be written to stdout/stderr in containers, collected centrally, processed through the logging pipeline, stored in Elasticsearch, and analyzed through Kibana.

---

# 76. Interview Question

### What information should never be logged?

**Answer:**

I would never log passwords, API keys, access tokens, private keys, database credentials, or unnecessary sensitive customer information. Logging should contain enough context to troubleshoot the issue while following security and data-protection requirements.

---

# 77. Interview Question

### How do metrics, logs, and traces work together?

**Answer:**

Metrics provide the high-level signal that something is wrong, logs provide detailed event and error information, and traces show the request path across services. For example, Grafana may show increased Payment latency, Kibana may show database timeout errors, and Jaeger may identify the database span as the slowest operation. Together they provide a complete troubleshooting workflow.
