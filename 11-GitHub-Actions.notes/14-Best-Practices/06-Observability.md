# Observability

Observability is the ability to understand the internal state and behavior of a system by analyzing the data it produces.

In DevOps, observability helps engineers answer:

    What Is Happening?
        +
    Where Is It Happening?
        +
    When Did It Start?
        +
    Why Is It Happening?
        +
    What Changed?
        +
    Is The System Recovering?

A practical observability stack can combine:

    Metrics
        +
    Logs
        +
    Dashboards
        +
    Alerts

In this environment:

    Prometheus
        |
        ↓
    Metrics

    Grafana
        |
        ↓
    Dashboards

    ELK Stack
        |
        ↓
    Logs

---

# 1. Observability vs Monitoring

Monitoring tells you:

    Something Is Wrong

Observability helps you understand:

    Why It Is Wrong

Example:

    Monitoring:
    CPU = 95%

    Observability:
    CPU increased after deployment
        +
    Request rate increased
        +
    Specific service is consuming CPU
        +
    Logs show expensive operation

# 15. Label Cardinality

Too many unique label values can create excessive time series.

Bad:

    request_id
        +
    user_id
        +
    session_id

as high-cardinality labels.

    service
        +
    method
        +
    status

Use labels carefully.

# 30. Latency

Latency measures request processing time.

Important values:

    P50
    P90
    P95
    P99

---

# 31. P50

P50 represents the median.

Example:

    P50 = 100 ms

Approximately half the observed requests are at or below this latency.

---

# 32. P95

Example:

    P95 = 300 ms

Approximately 95% of observed requests are at or below this latency.

The remaining requests represent the slower tail.

---

# 33. P99

Example:

    P99 = 800 ms

This highlights the slowest portion of requests.

---

# 34. Why P95 and P99 Matter

Average latency can hide slow requests.

Example:

    Average = 150 ms
    P95 = 400 ms
    P99 = 2 seconds

The average alone does not show the tail latency.

# 147. Interview Scenario

## Application Latency Suddenly Increases

Answer:

    I would first check the P95 and P99 latency to determine whether
    the problem affects the majority of requests or only the tail.

    Then I would check request rate, CPU, memory, database
    performance, external dependencies, and recent deployments.

    I would use Grafana to identify the affected service and ELK
    to inspect application errors and slow operations.

Flow:

    High Latency
        |
        ↓
    Grafana
        |
        ↓
    Identify Service
        |
        ↓
    Metrics
        |
        ↓
    ELK
        |
        ↓
    Logs
        |
        ↓
    Recent Changes
        |
        ↓
    Root Cause

# 148. Interview Scenario

## Error Rate Suddenly Increases

Answer:

    I would identify which service and endpoint are producing the
    errors.

    I would compare the error increase with deployment activity,
    request rate, latency, infrastructure health, and dependency
    failures.

    Then I would search the logs for the corresponding error pattern.

---

# 149. Interview Scenario

## Pods Are Restarting Frequently

Answer:

    I would first check the restart count.

    Then I would use kubectl describe pod to inspect events and
    kubectl logs --previous to identify the previous container
    failure.

    I would check for OOMKilled, probe failures, application
    crashes, and node-level issues.

---

# 150. Interview Scenario

## CPU Is High but Application Is Healthy

Answer:

    I would not immediately scale or restart the application.

    I would determine whether the high CPU is expected because of
    traffic or normal processing.

    I would compare current CPU against historical baselines and
    check application latency and error rate.

    If users are not impacted and the workload is expected, the
    high CPU value may not require immediate remediation.

---

# 151. Interview Scenario

## CPU and Latency Both Increase

Answer:

    This is more significant because resource saturation is now
    correlated with user-facing impact.

    I would identify the affected workload, check recent changes,
    determine whether traffic increased, and evaluate whether
    scaling or application optimization is required.

---

# 152. Interview Scenario

## Database Is Slow

Answer:

    I would correlate application latency with database metrics.

    I would check database CPU, memory, connections, storage,
    IOPS, query latency, and slow queries.

    I would also check whether a recent application deployment
    introduced inefficient queries.

---

# 153. Interview Scenario

## Queue Backlog Is Increasing

Answer:

    I would check producer rate, consumer rate, consumer health,
    processing time, and available capacity.

    If consumers cannot keep up, I would determine whether the
    correct solution is additional consumers, application
    optimization, or capacity changes.

---

# 154. Interview Scenario

## Monitoring Shows Everything Is Healthy but Users Report Errors

Answer:

    I would verify whether the existing metrics cover the actual
    user journey.

    I would check application logs, load balancer behavior, DNS,
    external dependencies, and business-level metrics.

    This can indicate an observability gap rather than a completely
    healthy application.

---

# 155. Interview Scenario

## Too Many Alerts

Answer:

    I would review the alert rules and determine which alerts are
    actionable.

    I would remove or tune noisy alerts, improve thresholds,
    combine related signals where appropriate, and define severity
    and runbooks.

Goal:

    Fewer
        +
    Higher-Quality
        +
    Actionable Alerts

---

# 156. Interview Scenario

## Prometheus Has Too Many Time Series

Answer:

    I would investigate label cardinality.

    I would identify high-cardinality labels and remove labels that
    are not required for operational analysis.

    I would avoid using values such as request IDs or user IDs as
    metric labels when they create excessive cardinality.

---

# 157. Interview Scenario

## Deployment Causes Performance Regression

Answer:

    I would compare the deployment timestamp with the performance
    metrics.

    I would compare:

    Before Deployment
        |
        ↓
    P95 / P99
        +
    Error Rate
        +
    CPU
        +
    Memory

with:

    After Deployment
        |
        ↓
    Same Metrics

    If the regression is confirmed and user impact is significant,
    I would use the rollback strategy and then investigate the
    change.
